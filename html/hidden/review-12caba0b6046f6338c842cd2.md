## Executive Summary

This specification proposes enhancements to Mnemosyne so agents can remember useful information across conversations and projects while respecting who may receive it, for what purpose, and with what supporting evidence. Semantic relevance is one input to recall. Trusted authorization must constrain the candidate set before ranking, prompt construction, evidence expansion, or provider submission.

The design keeps project relevance, sensitivity, compartments, audience, source trust, evidentiary status, content review, and retrieval eligibility as separate dimensions. One source can support several projects while each project's summaries and conclusions retain their own scope and restrictions. Selecting a project narrows recall within existing grants. Multi-participant contexts use the permissions common to all applicable participants, and protected operations fail closed when context or policy is invalid.

Every source-backed memory retains a path to an exact source revision and span. Stable identifiers survive file moves and duplicate copies; extraction corrections preserve history. Derived summaries and other memory layers inherit source restrictions, and corrections, revocations, or deletion propagate through affected derivatives and caches. Durable evidence has an explicit retention policy independent of working-memory trimming. Incremental imports are idempotent, resumable, and explicit about incomplete coverage.

Mnemosyne owns useful memories, associations, authorized recall, and evidence references. An archive application or adapter owns original bytes, physical locations, media preparation, and extraction jobs. Existing banks remain available for hard isolation, while existing media, resolver, annotation, and evidence-pack capabilities provide integration points for the proposed enhancements. Recall should return compact, relevant memory with authorized evidence available for expansion.

Mnemosyne is not a full-document or media archive. Complete source documents and raw traces remain external; the memory engine retains stable references, indexes, embeddings, compact derived memories, and bounded evidence excerpts. Policy enforcement is an optional capability for legacy deployments, but mandatory on every covered path once protection is explicitly enabled. Source integrity checks and performance comparisons are acceptance requirements, not claims about deployed behavior.

This document is a draft requirements specification. The handoff's source inspection identifies a development baseline; it does not establish current deployment or completed enforcement. The next step is to reconcile active Mnemosyne work, map implemented/partial/missing capabilities, and qualify a minimal prototype using synthetic data. Acceptance requires consistent access enforcement across all covered paths, preserved provenance, reversible migration, and measured recall quality and performance.

## Purpose

Agentic memory must not inject information merely because it is semantically relevant. It must also establish that the current conversation is authorized to receive that information. This specification defines a policy-aware memory model that works across changing sessions, communication channels, participants, clients, projects, legal matters, and regulated workloads.

The initial implementation target is Mnemosyne. The requirements are intentionally product-neutral so the policy model can also govern conversation extraction, document ingestion, consolidation, export, synchronization, and other memory engines.

This document is an engineering specification, not legal advice or a certification of HIPAA compliance, attorney-client privilege, work-product protection, or compliance with any jurisdiction's professional-conduct rules. Deployments in regulated or legal environments require review by the responsible privacy, security, compliance, and legal authorities.

## Design Inputs

HIPAA does not apply to every organization or every health-related record. Where it does apply, the Privacy Rule generally requires reasonable steps to limit uses, disclosures, and requests for protected health information to the minimum necessary for the intended purpose, subject to defined exceptions. HHS guidance describes role- or class-based access policies, categories of information, and conditions of access. The Security Rule adds administrative, physical, and technical safeguards, including access control, audit controls, integrity, person or entity authentication, and transmission security. Encryption alone is not sufficient. See the HHS guidance on the [minimum necessary requirement](https://www.hhs.gov/hipaa/for-professionals/privacy/guidance/minimum-necessary-requirement/index.html), [technical safeguards](https://www.hhs.gov/sites/default/files/ocr/privacy/hipaa/administrative/securityrule/techsafeguards.pdf), [cloud computing](https://www.hhs.gov/hipaa/for-professionals/special-topics/health-information-technology/cloud-computing/index.html), and [who must comply](https://www.hhs.gov/hipaa/for-professionals/faq/190/who-must-comply-with-hipaa-privacy-standards/index.html).

For legal practice, confidentiality is broader than a database privacy flag. ABA Model Rule 1.6 addresses information relating to representation and reasonable efforts against unauthorized access or disclosure. ABA Formal Opinion 512 applies duties including competence, confidentiality, communication, and supervision to generative-AI use. The ABA rules are model rules; controlling state rules, court orders, client terms, protective orders, and matter-specific obligations vary. See [ABA Model Rule 1.6](https://www.americanbar.org/groups/professional_responsibility/publications/model_rules_of_professional_conduct/rule_1_6_confidentiality_of_information/) and [ABA Formal Opinion 512](https://www.americanbar.org/content/dam/aba/administrative/professional_responsibility/ethics-opinions/aba-formal-opinion-512.pdf).

These sources motivate capabilities rather than hard-coded legal conclusions. The engine must provide configurable policy controls, provenance, auditability, and fail-closed behavior. An organization remains responsible for deciding which policies apply.

The Mnemosyne shared source and project memory requirements (internal supporting reference; not included in this packet), prepared October 14, 2026, adds a second use case: several projects share evidence while retaining separate interpretations, access rules, and durable source references. The source handoff remains authoritative for its archive-specific requirements and inspection evidence; its private evidence appendix must be omitted from publication and upstream submissions.

## Goals

- Prevent unauthorized memory retrieval and prompt injection across all retrieval paths.
- Preserve useful cross-session and cross-channel recall when the current context is authorized.
- Support public, internal, confidential, restricted, and private handling without requiring a separate database for every classification.
- Support client, patient, project, matter, team, ethical-wall, and other need-to-know compartments.
- Distinguish information a client or patient may see from internal analysis concerning that same entity.
- Classify conversation-derived memories from trusted context policy while keeping content-quality review separate.
- Classify documents independently because their origin path does not establish their permitted audience.
- Preserve Mnemosyne's low-latency and lightweight characteristics.
- Keep existing banks available for hard tenant, encryption-key, residency, or legal-isolation boundaries.
- Support shared source evidence across authorized projects while keeping each project's memories and interpretations separately scoped.
- Preserve exact evidence references through relocation, duplicate copies, extraction corrections, and incremental indexing.

## Non-Goals

- Determining whether a record is legally privileged, protected work product, PHI, or subject to a legal hold.
- Replacing identity providers, authentication, consent management, records management, encryption, backup, or incident response.
- Inferring authorization from a chat title, mutable display name, or ephemeral session ID.
- Claiming that use of this feature makes a deployment compliant with any law or professional rule.
- Automatically downgrading information so it can be shown to additional participants.
- Owning archive byte storage, disk discovery, bulk conversion, media preparation, transcription/OCR jobs, or human archive organization; those remain archive or adapter responsibilities.

## Terminology

**Principal:** A human, agent, service, or organization with a stable authenticated identity.

**Context:** A security-relevant conversation or work scope resolved from trusted platform claims, participants, channel identity, project or matter identity, purpose, and policy version. A context may span multiple runtime sessions.

**Classification:** A handling sensitivity such as `public`, `internal`, `confidential`, `restricted`, or `private`. A deployment defines the ordering and semantics. `private` may be modeled as a restrictive level for compatibility, but personal ownership and audience restrictions must remain separate attributes.

One optional reference profile uses Unclassified, Confidential, Secret and Top Secret as described below, with an explicit organizational namespace. Other domains configure their own ordered levels and display labels. Existing `private`, `restricted`, `internal` and `public` labels remain legacy/custom vocabulary, not additional U.S. national-security classification levels or automatically equivalent aliases. Unclassified is not a public-release authorization. A label's meaning depends on its exact policy identity/version.

**Compartment:** A need-to-know domain such as `client:acme`, `matter:smith-v-jones`, `patient:1234`, `project:atlas`, or `ethical-wall:merger-a`.

**Audience:** Explicit principals, groups, or relationship classes allowed to receive a memory, such as `client-visible`, `care-team`, `firm-internal`, or `owner-only`.

**Purpose:** The declared use under which access is evaluated, such as `treatment`, `billing`, `client-service`, `matter-work`, or `operations`. Purpose does not create access by itself; policy must authorize it.

**Clearance:** The maximum classification a principal or context may receive. Authentication assurance and trust are inputs to policy, not synonyms for clearance.

**Access eligibility and read-in:** A separately attested entitlement to participate in a particular compartment or controlled activity. For this software, these are explicit host-managed grants, not real government vetting or a government-issued agent clearance. Need-to-know and handling controls still apply after eligibility is established.

**Handling overlay:** Additional applicable requirements governing use, disclosure, recipients, providers, retention or other actions independently of classification rank. Examples include HIPAA PHI, legal confidentiality, a matter-specific protective order or a genuine CUI category. A stored overlay label alone is not an enforcing rule or a compliance conclusion.

**Context epoch:** A stable version of a context's participants and policy. A participant, purpose, or authorization change creates a new epoch and forces re-evaluation.

**Project membership:** A relevance association between a source or memory and zero or more projects. It records origin, assigning actor, and proposed or confirmed state. Membership does not grant access; a project may separately require a compartment under the configured policy.

**Source identity:** A stable logical source identifier, distinct from an immutable byte revision, physical occurrence, extracted representation, and derived memory. Existing asset IDs should be reused where they already represent that source.

**Source trust:** The authority of content to influence instruction handling. Imported sources remain data even when reviewed, sensitive, or useful as evidence.

**Evidentiary status:** Whether a statement is a quotation, recollection, allegation, inference, or verified finding. This is separate from sensitivity, review state, source trust, and project membership.

## Threat Model

The design must address accidental cross-client recall, prompt injection that attempts to retrieve restricted memories, stale authorization after participant changes, mutable titles or reused channel names, post-filter leaks from vector or full-text search, derived memories with lost provenance, cache reuse across security contexts, unauthorized export or synchronization, and adapters that omit or forge context claims.

The memory engine may trust an adapter only after it has authenticated the platform and supplied stable principal and context identifiers. Untrusted or incomplete context fails closed to the least-privileged policy configured by the deployment.

## Information Model

When protected policy is configured, every durable memory and derived chunk must carry policy fields as indexed first-class data, not an opaque metadata blob. The example below describes a protected row; it is not a required retrofit of every legacy row before an unconfigured deployment can operate:

```yaml
memory_id: mem_01...
classification: confidential
compartments:
  - client:acme
  - matter:acme-contract-2026
audiences:
  - firm-internal
purposes:
  - client-service
owner: org:example-law
origin_context_id: ctx_01...
origin_context_epoch: 4
classification_source: context
policy_version: 3
source_ids:
  - message:telegram:...
derived_from:
  - mem_00...
created_at: 2026-07-17T00:00:00Z
review_state: automatic
classification_policy: "[[Wiki/Policies/Document Classification Policy]]"
```

At minimum, the schema must support:

- classification and classification source;
- zero or more compartments, audiences, and allowed purposes;
- owner or tenant;
- immutable source and derivation provenance;
- originating context and epoch;
- policy version used at creation and at the latest decision;
- lifecycle state, retention or hold references, and reclassification history;
- explicit review state independent of security classification;
- explicit source and memory project memberships, including assignment provenance and proposed or confirmed state;
- exact source revision, extraction revision, span, speaker attribution, and evidentiary status where applicable.

Classification labels alone are insufficient. A confidential memory for one client must not be available in another confidential client context.

### External-source storage contract

Original documents, web-page captures, photographs, images, audio/video recordings, full transcripts, complete conversation/tool traces, and derived full-file renditions remain outside Mnemosyne's database and engine-owned sidecar directories. A sidecar copy is still an archive copy and is not a loophole in this contract. The owner-selected filesystem, Obsidian Vault, object store, or archive service retains those bytes. Mnemosyne owns the indexes and memory records needed for recall, not a replacement collection of original files.

Mnemosyne may retain stable source/revision handles, resolvable URIs, verification metadata, project/policy relationships, embeddings and lexical indexes, compact summaries/facts, and bounded evidence excerpts with exact locators. Indexing may read a complete authorized source transiently to extract and index it; it must not persist the full extracted document as a parallel text archive or reconstruct one through unbounded excerpt retention. Record excerpt-size and aggregate per-source retention limits as part of the indexing contract; do not silently truncate an original or discard its external recovery location. A complete search index need not imply a complete readable source copy in memory.

Indexes, embeddings, hashes, captions, and OCR excerpts are sensitive derivatives, not anonymized or guaranteed non-reconstructable representations. They inherit source restrictions even when no original bytes are stored. Lexical indexing must not hide a complete readable document in a stored-content field merely because it is called an index; the planning review must reconcile full-source search coverage with the bounded-content contract and backend capabilities.

Support reference-only registration even when no extraction/vision provider is available. Reuse the inspected MediaStore vocabulary for image, video, audio, and document assets, captions/OCR regions, and page/time/character/bounding-box spans where supported. Those development-source capabilities are not evidence that the older live runtime implements them. New file types require an explicit adapter capability and degradation behavior, not a second source-storage subsystem. Remote extraction, vision, transcription, and embedding destinations remain optional and must obey the configured access/destination policy.

A URI is a locator, not sufficient source identity or permission. Retain a stable source ID and immutable revision alongside authorized resolver locations, using `archive:`, `file:`, or HTTPS references as supported by the adapter. Do not retain credentials or reusable signed access URLs in ordinary memory records. Resolve handles only through allowed schemes, destination/root constraints, and trusted configuration; an imported or model-supplied URI cannot authorize arbitrary filesystem or network access.

Mnemosyne's policy protects indexed/derived content and access through its APIs and resolvers. It cannot enforce permissions on an original opened directly outside those paths. The archive, filesystem, or web service must independently enforce compatible access controls; a restricted memory record does not make an otherwise public source private.

### Checksums and source-change detection

Storing a hash does not establish that a source is still unchanged. Record the hash algorithm (SHA-256 initially), source-byte digest when available, verification time, verification method, and verification state. Reference-only registrations without readable bytes remain explicitly unverified; no synthetic checksum is substituted. Source hashes, extracted-text hashes, and embedding identities are different fields. A byte hash identifies content, not authorship, authenticity, or an access grant.

An adapter or archive integrity job performs explicit revalidation on owner request, configured deterministic schedules, or evidence expansion. Ordinary recall must not reread/hash whole originals, scan volumes, or trigger extraction/vision/transcription requests. It may use the configured authorized query-embedding path; that is not source hydration. Verification scheduling is housekeeping, not an LLM task. The memory record tracks the result and check time, including checks that could not complete.

| Observation | Required result |
| --- | --- |
| Same URI and matching source-byte hash | Retain the existing revision; update verification metadata without duplicate memories or embeddings |
| Same URI and different bytes | Create an immutable new byte revision; retain prior provenance and mark dependent results stale until explicitly reconciled |
| Different URI and identical bytes | Record another occurrence of the same revision within the permitted sharing domain; preserve identity |
| Same bytes, corrected extraction | Retain the byte revision and create an extraction revision/supersession; invalidate only affected derivatives |
| Missing, offline, inaccessible, or unsupported source | Record the distinct verification state without claiming a match, deleting evidence, or broadening access |

For web sources, define the exact fetched representation being hashed, including relevant content/transfer decoding and capture metadata. A URL does not identify an immutable page. ETag, Last-Modified, file size, and mtime are revalidation hints, not replacements for a verified byte digest; a not-modified response is not a fresh cryptographic verification. The external archive may retain historical web captures; Mnemosyne must not claim that today's response proves the content of an earlier revision. Normalized/extracted-text hashes may avoid unnecessary re-embedding under a matching processing contract without hiding the byte change.

On explicit evidence expansion, verify the expected revision before presenting bytes as that evidence. A mismatch returns changed-content rather than silently serving a newer version under an older citation. Authorized retained memories may still recall while a source is offline or known to have changed, but must carry their revision and stale/unverified status rather than imply current-source verification. Derivative refresh and policy revocation are distinct: access restrictions take effect immediately even if extraction or checksum work is pending.

### Source identity and extraction lineage

Maintain one source catalog within an explicitly defined ownership and access domain. Reuse Mnemosyne's existing media assets, moments, resolvers, annotations, and evidence packs rather than introducing parallel systems. Source identity may be shared across authorized banks without a shared writable database or implicit cross-bank search. The archive owns physical occurrences and processing-job state; Mnemosyne stores stable handles and the fields needed for memory, authorization, and evidence expansion.

A changed file at the same path creates a new byte revision. An identical copy at another path creates an occurrence of the existing revision. An asset registered by reference retains its ID when a hash becomes available. Hash lookup and deduplication must remain within the permitted ownership/access domain and must not reveal another principal's matching material. Identical words in separate utterances remain separate evidence; duplicate exports do not count as independent corroboration.

Source-backed memories must expand to an exact revision and span. Reuse page, time, and character spans, and support external message IDs, attachment/member locators, and JSON pointers when supplied by adapters. Preserve source speaker labels and distinguish confirmed identity mappings from recognition guesses. Record original media, prepared renders, transcription chunks, raw transcripts, corrections, and derived memories as related artifacts with tool/model/version/settings, input/output hashes, processing time, review state, and offsets. A corrected extraction at an existing span must retain a representation revision or explicit supersession; span idempotency must not silently discard it.

Recorded time, historical event time, ingestion time, and media-relative offsets are distinct fields, with timezone and precision where known. Gaps and unknown dates remain explicit. Contextual reconstruction carries an inference label and cannot be presented as a transcript of a missing event.

### Project selection and evidence resolution

Shared evidence can support distinct project summaries and conclusions. Those derivatives retain their own memberships and provenance; sharing a source does not make its interpretations globally available or eligible for persona injection. Adding membership neither grants access nor lowers restrictions. Sharing a source or excerpt is an explicit operation recording actor, recipients/projects, permitted span, rationale, and policy revision.

Memories reference opaque archive/source/revision handles. Archive resolvers map them to verified current occurrences and retain location history. A location change alone changes neither memory/span IDs nor embeddings. Resolution distinguishes available, offline, missing, changed-content, unsupported-resolver, and unauthorized states while protecting inaccessible locations and object existence. Authorized retained text may still recall when its source volume is offline. Ordinary recall does not hydrate source bytes, scan disks, or invoke source-understanding providers; configured authorized query embeddings are permitted. Explicit expansion/hydration rechecks current policy, enforces destination rules, prevents symlink escapes, and verifies the expected revision before returning bytes.

## Context Resolution

A `ContextResolver` converts authenticated platform claims into an `AccessContext`. Platform adapters may use different native identifiers, but must produce the same canonical shape:

```json
{
  "context_id": "ctx_01...",
  "epoch": 4,
  "platform": "telegram",
  "channel_id": "example-channel",
  "conversation_id": "topic-or-thread-id",
  "principals": ["person:operator", "person:client-contact"],
  "classification_ceiling": "confidential",
  "compartments": ["client:acme", "matter:acme-contract-2026"],
  "audiences": ["client-visible"],
  "purpose": "client-service",
  "policy_version": 3,
  "assurance": "authenticated"
}
```

The registry behind the resolver must persist independently of runtime session IDs. A title may help an operator locate a context policy but must never be the sole authorization key because titles are mutable and non-unique.

When participants differ across platforms, the effective context must use the least-authorized combination. The effective classification ceiling is no higher than the lowest participant clearance and the configured context ceiling. Effective compartments are the intersection of the context's compartments and every participant's applicable compartments. Audience and purpose rules are then applied. Unknown principals, unresolved participant sets, unknown policy versions, and ambiguous mappings fail closed.

An agent's broader independent privileges must not enlarge that intersection. A memory accessible to the agent elsewhere is ineligible for retrieval or prompt injection here unless every applicable participant and the current context authorize it. Stale context epochs and incomplete participant mappings fail closed; a model's assertion that all participants are authorized is not trusted evidence.

Trusted context must also carry permitted banks/projects, operations, and destinations. Query arguments may narrow those grants but cannot select a more privileged principal or expand authorization. Project selection is query intent: an explicit union of selected projects, intersected with trusted grants and every applicable restriction. Empty selection, unknown projects, malformed policy, legacy rows, and an explicit all-authorized-projects mode require documented semantics without accidental broadening. An in-process SDK must document its trusted-owner mode; API filtering cannot constrain a process with unrestricted direct database/filesystem access.

## Authorization Decision

A memory is eligible only when all applicable checks pass:

1. The memory's classification does not exceed the effective context ceiling.
2. Every required memory compartment is present in the effective context compartment set.
3. Audience, owner, tenant, purpose, consent, hold, and policy-overlay rules allow the operation.
4. The adapter supplied an authenticated context at the assurance level required by policy.
5. The policy decision is current for the context epoch and policy version.

Conceptually:

```text
allow(memory, context, operation) =
    level(memory) <= ceiling(context)
    AND compartments(memory) subset_of compartments(context)
    AND audience_allows(memory, context)
    AND purpose_allows(memory, context, operation)
    AND overlay_allows(memory, context, operation)
```

This is a partial-order policy, not just role-based access control. Implementations may compile it into indexed predicates and cached decision plans, but cannot weaken the result.

## Conversation-Derived Memory

Conversation records inherit the strictest effective security policy of their originating context. A memory derived from multiple messages or memories receives the highest classification, the union of required compartments, and the most restrictive audience and purpose constraints among its sources unless an authorized reclassification workflow explicitly changes it.

This supports deterministic conversation extraction without asking a model to classify access. Extracted Markdown may be created with:

```yaml
classification: confidential
classification_source: context
classification_reviewed: automatic
review_state: pending
context_id: ctx_01...
context_epoch: 4
compartments:
  - client:acme
mnemosyne: exclude
```

Security classification and content-quality review are separate. Automatic context classification can be authoritative for access while the extract remains pending review for usefulness, formatting, filing, linking, and eventual indexing. Empty or low-value extracts may move to `Discard` without weakening audit provenance.

If a participant joins, leaves, loses access, or changes role, the system creates a new context epoch. Memories from the prior epoch are not reclassified and remain subject to their original restrictions.

**Fresh-context rule:** when the audience's effective authority narrows, stop the prior protected turn and require a new clean security/model context before continuing. Do not sanitize or edit the old model history in place as an alternative. The conservative default is a fresh context whenever a new person or agent joins, including equal-clearance participants whose scopes may differ. Unknown audience/permission mappings remain denied until resolved; an empty new context is not an authorization fallback.

Fence old provider/tool work, output queues, retries, evidence handles and context-bound state before admitting the new audience. A clean context must not reuse the old provider conversation, prompt/KV state, hidden reasoning, transcript, tool results, persona/prelude or cached conversation summary. Independently retrieved evidence must satisfy the new audience and current authority. If a frontend cannot establish the fresh boundary, refuse protected continuation rather than rely on the model to forget. Freshness here is a host/provider capability requirement, not a demand to erase historical records or every immutable cache entry regardless of its supported authorization contract.

Keep the prior transcript under its original access restrictions; joining a new audience must not reveal old messages, attachments, previews, notifications or retained summaries through the UI/history APIs. Usually the safest presentation is a separate conversation, not adding someone to a thread that exposes its existing history. Already emitted information cannot be retracted, but late old-epoch responses must not be delivered to the new audience.

Continuity summaries are optional, not a prerequisite for continuing safely. Rebuild them in a fresh context from independently authorized source evidence, or use a separately approved, provenance-bearing release artifact whose current policy permits this audience. Do not ask the old privileged model context to produce a supposedly sanitized handoff and treat its output as lower-classified. A summary normally inherits its sources' restrictions; reducing those restrictions requires an explicit authorized release/reclassification workflow. If no safe handoff exists, start without one. Planned transition checks are [T01-T06](/hidden/review-2d66666c7be62e65c7daf868/policy-profiles/#fresh-context-transition-checks); this is a design requirement, not implemented frontend acceptance.

## Document Handling

Documents do not automatically inherit a safe classification merely because they appear in a directory or were attached to a conversation. Each document must have explicit policy metadata from a trusted source, an approved folder policy, or a human-reviewed classification workflow.

When classification is absent and no trusted context, source, or inheritance rule supplies it, the default classification is `unclassified`. Record that the label came from a default rather than an explicit classification decision. This default does not replace a stricter inherited classification, remove compartments, change ownership or audience, or grant access. `Unclassified` is a sensitivity label, not a synonym for public or open to all. Otherwise valid protected policy may authorize an unclassified record; missing classification alone need not quarantine it once this normalization contract is implemented.

Missing required access-policy metadata, or invalid, contradictory, or unsupported classification/policy values, must remain pending and excluded from protected retrieval. An invalid explicit classification must not be silently downgraded to `unclassified`. Classifier-assisted suggestions are advisory until accepted unless a deployment has explicitly approved a deterministic policy source. Existing unconfigured legacy behavior is unchanged; the default is a requirements decision, not authorization to rewrite existing records or enable protection.

Document policy must support client- or patient-visible material and internal material concerning the same entity. For example, both documents may carry `client:acme`, while audiences distinguish `client-visible` from `firm-internal`. Legal labels such as privilege, work product, protective-order status, and legal hold are policy attributes or external references, not conclusions the memory engine invents.

Document classification has separate outputs: sensitivity/handling policy, project relevance, source trust, evidentiary status, review state, and retrieval eligibility. A suggested project assignment cannot authorize retrieval. Reviewed imported content remains data. Conflicting accounts must remain representable; a transcript, email, or prior assistant answer does not become a verified fact merely through ingestion or repetition.

### External Document Control And Policy Bindings

Document control and entity access control are separate, conjunctive responsibilities: the source/revision has current sensitivity and handling restrictions; authenticated people/agents have explicit scoped permissions; the actual conversation, purpose and destination constrain their intersection. A configuration administrator receives no content permission merely by assigning labels. Domain-facing terms and worked government/contractor, healthcare, legal, personal and generic examples are in the [profile guide](/hidden/review-2d66666c7be62e65c7daf868/policy-profiles/#worked-domain-profiles). A service/agent processing ceiling is not a government-issued personnel clearance or a professional credential.

All external formats require a stable source/revision identity and a current accepted policy binding within the permitted ownership domain. Reuse existing source/asset, revision and policy facilities. Markdown front matter, Office/PDF metadata, embedded labels and portable sidecars may convey classification indications or source/policy references; untrusted editable metadata does not become authorization or release authority. The authoritative external document-control system may own the accepted binding, which Mnemosyne consumes and tracks for derived-policy enforcement. This is not a requirement for one global database, a separate mandatory service or a new full-document archive.

File locations and source-byte revisions are distinct from policy revisions. Moving a file changes its occurrence, not its rights; changing accepted handling can advance current policy without altering original bytes. Editing front matter/embedded metadata changes bytes and requires the corresponding byte revision. Source checksums do not prove permission freshness; policy signatures alone do not prove that an old permission remains current. Required policy revocation/invalidation cannot wait for rereading originals, checksum jobs or re-embedding.

One source shared across authorized projects retains its accepted policy; do not elect a different authoritative sidecar per project or union project-reader permissions. Derivatives inherit the source restrictions and may add stricter ones. A less-restricted subset requires an independently identified, authorized reviewed release/redaction with exact lineage. General joint-policy composition is not yet implemented: an unrepresentable or unsupported required control denies rather than selecting the looser domain. Cross-owner hash matching cannot expose another owner's existence or grant content access.

Treat whole-file restrictions as the default across hidden sheets/rows, comments, revisions, slide notes, attachments and other embedded material. A lower-granularity representation needs qualified extraction and policy inheritance; do not send denied material to an internal parser/model/ranker that lacks authority and filter afterward. A required but unsupported parser/protection/translation path refuses. Existing external encryption and labeling must not be stripped merely to enable indexing.

A URL is an occurrence/reference, not a public-access grant. A reachable object may require authentication, have been shared privately or exposed without authorization. Even a released public source can have restricted project associations and derivatives. Capture/revision verification, actual use/recipient/provider authority and approved resolver/redirect behavior remain separate checks. Missing/conflicting sidecars or required access metadata never trigger a public downgrade; the accepted `unclassified` default above remains nonpublic and does not supply missing permissions. Cross-format scenarios [D01-D10](/hidden/review-2d66666c7be62e65c7daf868/policy-profiles/#additional-documentation-acceptance-scenarios) are proposed acceptance requirements, not executed or deployed capabilities.

## Retrieval and Prompt Injection

Policy filtering must occur before candidate content can be returned to application code, ranked into a prompt, exposed by tools, logged, cached, consolidated, exported, or synchronized. Post-filtering a broad unauthorized result set is not an acceptable primary control.

There is no exception for privileged memory retrieved for internal reasoning in a shared conversation. Authorization constrains vector/FTS/graph candidate generation before restricted candidates reach application code or ranking, and applies again at expansion, reranking, tool-result, prompt-assembly and provider-submission boundaries. Final-answer filtering cannot undo contamination of a model context, ranker or tool. Trusted policy-index evaluation is distinct from materializing restricted candidate identities or content for those consumers.

The same authorization predicate must govern:

- vector retrieval;
- full-text search;
- facts, entities, and knowledge graphs;
- working and episodic memory;
- consolidation and summarization;
- shared-memory and administrative tools;
- cache entries and cached prompt fragments;
- export, import, backup, synchronization, and debugging interfaces.
- polyphonic and enhanced recall, direct-ID lookup, evidence-pack expansion, persona/profile injection, task memory, and source hydration.

Every result must retain memory ID, policy decision ID, bank, source, classification, and compartment provenance. Prompt-injection code should receive already-authorized results and must not have a bypass that omits policy context.

Cache keys must include a stable context-policy fingerprint containing at least the effective principal set, context epoch, classification ceiling, compartments, audience, purpose, operation, and policy version. Policy changes invalidate affected caches.

Keys must also include selected projects, permitted destinations where relevant, and applicable source/extraction revisions. Candidate generation must prevent inaccessible high-ranked rows from starving authorized results. Policy applies before content reaches a model, reranker, or external provider, including during evidence-pack expansion. Counts, titles, filenames, denied-object errors, and diagnostics must not reveal inaccessible material. Evidence handles are reauthorized when expanded; a previously issued handle does not confer perpetual access. Revocation governs system-managed data and cannot retract text already disclosed or copied externally.

## Configurable Profiles And Administrative Separation

Keep one generic policy engine. Each versioned domain profile defines stable policy/level IDs and ordering, user-facing and administrator-facing terminology, compartment and audience vocabularies, allowed actions/purposes, and references to supported reviewed handling rules. Medical, legal, government-inspired and personal profiles are data/configuration choices, not branches hard-coded as organization names or law names in retrieval logic. Display aliases do not authenticate, authorize, reclassify or change stored policy identities. Unknown rules or versions refuse; renaming a field cannot implement an absent rule. See the [configuration guide](/hidden/review-2d66666c7be62e65c7daf868/policy-profiles/) for the proposed format, current API example, limitations and domain setup workflow.

Separate administrative capabilities from content grants. A configuration administrator may manage approved profiles/settings without permission to recall documents, browse private filenames, read conversation history or view sensitive audit details. Content readers have independent classification, need-to-know, purpose and recipient grants. Administrative visibility is itself bounded; some profile names, patient/matter identifiers and grant relationships require separate metadata-administration scope.

Distinguish presentation-only edits from security-semantic edits. Changing level ordering, identity mappings, group membership, audiences, rule references, provider routes, defaulting, approval policy or key/restore authority can expand access even without a direct recall grant. An ordinary configuration role cannot make these changes to elevate itself or controlled agents/groups, including indirect delegation or replacing the approval policy. Use explicit bounded grant/policy-administration capabilities, exact-predecessor preview, separately authorized approval where required and content-free audit. A single operator may intentionally hold multiple roles, but that assignment must be explicit; do not infer all-powerful administration from a generic admin flag.

The raw platform/key owner remains a separate trust boundary: an unrestricted deployment administrator who can replace enforcement code or obtain keys is not constrained by an application-level configuration role. Keep those capabilities outside ordinary administrator and model-controlled tools when claiming separation. Administrative recovery/break-glass authority, if supported later, is explicit, scoped and audited, not automatic blanket access. No role or permission is provisioned by this documentation revision.

## Government-Inspired Reference Profile

Use familiar government/military terminology as one configurable reference profile. [Executive Order 13526, sections 1.2 and 4.1](https://www.archives.gov/isoo/policy-documents/cnsi-eo.html) distinguishes three classified levels and requires eligibility, an approved nondisclosure agreement and need-to-know for access. Our organizational analogue keeps those concepts separate; it cannot issue official clearances or authorize actual national-security processing.

| Display name | Proposed reference label | Role in the organizational analogue |
| --- | --- | --- |
| Unclassified | `unclassified` | Bottom reference rank; no national-security classification asserted; access may still be private or regulated |
| Confidential | `confidential` | First classified-style organizational sensitivity tier |
| Secret | `secret` | Higher organizational sensitivity tier |
| Top Secret | `top_secret` | Highest tier in this reference profile, not universal access |

Unclassified is included as the base for comparison, not a fourth classified level. The reference policy identity is proposed as `organizational-us-inspired/v1`; this is not a registered/installed profile ID. Interfaces must identify the namespace, for example "organizational clearance", rather than implying government-issued credentials. Do not apply national-security damage definitions to clinical or legal records to justify artificial government classification. Actual government-classified source handling remains unsupported in the current development/deployment scope.

Use compartments and explicit access/read-in grants for client, matter, patient, project or other need-to-know domains. Special-access controls are not extra steps above Top Secret. Dissemination controls, provider approvals and release decisions are independent predicates. A persona can select an authenticated registered agent identity; a trusted host/chat binding can impose a context ceiling; every applicable participant still constrains the result. A mutable persona name or chat ID is never a credential by itself.

Credentialing and suitability/fitness (including Public Trust position requirements) are independent from national-security classified-access eligibility and cannot supply or substitute for a Confidential/Secret/Top Secret ceiling. SCI eligibility and actual current control-system/compartment access are distinct required attestations when applicable, not a `SCI` level above Top Secret or an entitlement inferred from project membership. The [worked eligibility/access examples](/hidden/review-2d66666c7be62e65c7daf868/policy-profiles/#worked-tssci-access-example) include a Public Trust-only requester, wrong-compartment requester and expired mission/read-in. Healthcare role/patient and legal matter/screen/order restrictions are functional policy analogies, not equivalent official credentials. These distinctions do not implement vetting, professional credentialing, regulatory evaluation or real classified-processing authorization.

```text
effective ceiling = minimum(chat ceiling, all applicable principal ceilings)
eligible record = matching policy/version and rank within effective ceiling
                  AND authorized owner/tenant and selected project scope
                  AND every required compartment/read-in satisfied
                  AND permitted audience, purpose, action and destination
                  AND every applicable handling-overlay decision satisfied
                  AND current context, grant, lineage and restore authority
```

No one of these conditions substitutes for another. Strong credentials or a Top Secret organizational ceiling do not grant access to every client, patient or purpose. An empty shared permission set refuses; it is not permission to borrow the agent's wider independent grants. This is a proposed profile composition rule, not a claim that every overlay is implemented by the current core.

Controlled Unclassified Information is a separate safeguarding/dissemination framework, not a rank between Unclassified and Confidential. Its governmental applicability must be established; do not designate ordinary private health/legal material as actual CUI solely because it is sensitive. Private and public-release states likewise remain separate from rank. See the [NARA CUI definition](https://www.archives.gov/cui/registry/cui-glossary.html).

### Regulatory And Professional Overlays

Use **HIPAA** for the Health Insurance Portability and Accountability Act; "HIPPA" is not the policy identifier. ABA here means the American Bar Association's professional-conduct model, interpreted through the controlling jurisdiction's adopted rules and matter-specific obligations. Neither is a sensitivity level, and neither can be reduced to "HIPAA equals Confidential" or "attorney data equals Secret".

The following are proposed control mappings, not complete executable legal rules. Applicability, jurisdiction, effective policy revision, source of authority and any consent/exception evidence must be resolved by trusted authorized policy administration. The model must not invent them from document text. Unknown required applicability or conflicting obligations keep the covered operation denied pending a resolved policy decision; do not silently choose a more convenient label.

This is an extensibility boundary, not a claim to implement every regulation. Multiple applicable overlays compose conjunctively; unresolved legal conflicts need an explicit authorized resolution, not a generic "highest clearance wins" shortcut.

Provider handling is part of the decision, not just user access. HIPAA-covered cloud processing can require business-associate arrangements and other safeguards; encryption or a locally running model alone does not establish compliance. ## Legal Policy Profile

A legal deployment may define client, matter, team, co-counsel, court, vendor, and ethical-wall compartments. Audiences may include client-visible, matter-team, firm-internal, opposing-party-visible, court-filed, owner-only, or specifically named principals.

The design must support:

- one client with multiple matters and different matter teams;
- one matter containing client-visible and attorney-internal memory;
- participants authorized for one project or matter but not another;
- ethical walls and conflict groups;
- outside counsel, experts, and vendors with bounded access;
- protective-order and jurisdiction-specific overlays;
- retention, preservation, and legal-hold references;
- explicit approval for declassification or broader disclosure.

No generic AI policy can determine whether information is privileged, whether privilege was waived, or whether work-product protection applies. Those decisions must come from authorized people and controlling policy.

## Banks and Isolation

Named Mnemosyne banks remain useful for hard isolation such as separate tenants, encryption keys, data residency, regulated environments, or a legal boundary that prohibits shared storage. They should not be the primary mechanism for routine classification.

A policy-aware store can support deduplication, cross-context retrieval, lifecycle management, and operational simplicity within an allowed sharing domain. It must still enforce authorization inside every query path. A deployment may combine both models: choose authorized hard-isolation banks first, then apply per-memory policy within each bank. Shared stable source identifiers do not require merging banks or searching them implicitly.

Migration from separate general and private banks must be side-by-side, reversible, and provenance-preserving. Duplicate memories must be reconciled without dropping the stricter policy. The original stores remain available until authorization, recall, integrity, and rollback tests pass.

Proposed authorization is opt-in for unconfigured legacy deployments and fails closed once protected policy is configured. Restoring legacy rows must not silently classify them as public or grant new project access. Document owner-mode compatibility and migration behavior explicitly. Until enforcement parity is demonstrated, existing separate banks/indexes remain the isolation boundary.

### Optional policy and compatibility contract

Normative classification/context/denial requirements in this specification apply to protected operation unless explicitly stated otherwise. General source-integrity and external-storage requirements apply independently of policy activation. Existing unconfigured deployments retain their documented APIs, bank/scope behavior, and existing isolation controls; they are not required to add policy metadata or adopt a new service to continue operating. Descriptive legacy metadata alone neither activates protection nor demonstrates that it is enforced.

Classification vocabulary and user/administrator terminology are profile-defined. The government-inspired vocabulary is an optional example, not a hard-coded default or mandatory retrofit; legal/healthcare overlays apply only under an explicitly selected and qualified policy. An external policy service and third-party identity infrastructure remain optional. Domain examples do not change the legacy default or claim regulatory certification.

| Mode | Compatibility and enforcement contract |
| --- | --- |
| Legacy/unconfigured | Preserve the documented existing behavior and bank isolation; do not claim new memory-level authorization guarantees |
| Explicitly protected | Persist activation and policy revision for the protected bank/domain; enforce trusted context and indexed access constraints on every covered read, write, expansion, and maintenance path |
| Protected but missing/invalid policy, context, or adapter capability | Refuse the protected operation with a content-free diagnostic; never fall back to legacy behavior |

Once activation is persisted, deleting a config key or using an older client must not disable enforcement. Disabling protection or moving protected data to legacy operation requires a separately authorized, auditable transition, not an implicit fallback. A trusted request to register protected material in a domain that cannot enforce it must be refused rather than stored with a misleading protected label. Restored protected stores retain their activation and restrictions; legacy rows newly introduced into a protected domain remain excluded/pending until a trusted compatibility mapping is accepted.

Restoring an older database, policy snapshot or software artifact must not silently revive revoked grants. Define the authoritative current policy/epoch and reconcile restored state before permitting access; where freshness cannot be established, protected operations remain denied. A usable data backup is not authority to roll back authorization history.

Activation requires an explicit inventory of supported and unsupported paths, including BEAM working/episodic memory, vector/FTS recall, graph/fact retrieval, canonical/persona injection, evidence/resolver expansion, caches, consolidation, exports, synchronization, SDK, CLI, MCP, and Hermes integration. An unsupported path cannot access protected records. Constraints belong at the trusted storage/candidate-generation boundary as well as adapter boundaries, not only in a front-end wrapper or a JSON label checked after broad retrieval. Existing databases must not be silently merged, reindexed, or migrated to enable the feature.

Provider ownership is a separate correctness prerequisite: session/profile/bank routing and attribution must remain correct under overlapping calls and session changes. Policy cannot repair a write sent to the wrong database. Require synthetic real-dispatch tests for the pinned host/adapter pair, including public/private A/B/A interleaving, before claiming protection across those contexts. Agent arguments and session-label parsing cannot supply privileged identity. Keep existing banks as the isolation boundary until these and cross-path policy tests pass.

The October 18 review identified [upstream issue #1188](https://github.com/mnemosyne-oss/mnemosyne/issues/1188) as relevant evidence for this qualification boundary: released provider pairs have reproduced cross-profile misrouting, while newer development results cover specific routing cases rather than universal Gateway acceptance. This is not proof of disclosure in our deployment, a released-upgrade recommendation, or approval to apply a session-parsing workaround. Resolve applicability using the exact host/provider dispatch and synthetic data, not new production canaries or private-memory inspection.

## API Requirements

When protected policy is configured, all memory operations must require an explicit trusted context or an explicit administrative policy capability.

The following calls illustrate the policy contract; implementation must first reconcile existing APIs and active development rather than commit to new public names:

```python
memory.remember(content, context=access_context, provenance=source)
memory.recall(query, context=access_context, limit=10)
memory.forget(memory_id, context=access_context)
memory.reclassify(memory_id, decision=approved_decision, context=admin_context)
```

The API must return or record a structured decision:

```json
{
  "decision_id": "dec_01...",
  "allowed": true,
  "operation": "recall",
  "policy_version": 3,
  "context_fingerprint": "sha256:...",
  "reason_codes": ["LEVEL_ALLOWED", "COMPARTMENTS_ALLOWED", "AUDIENCE_ALLOWED"]
}
```

Adapters must not synthesize privileged defaults when context is missing. Administrative inspection must be a separately authorized operation and should redact content unless content access is necessary.

The combined integration surface must support source-revision registration, project/policy association, versioned extraction and derivation links, token-budgeted project recall, authorized exact-evidence expansion, policy-preserving export/import, and project-scoped coverage reports. Reports distinguish missing/offline sources, stale derivatives, and index generation without exposing unauthorized metadata.

## Audit and Lifecycle

Audit records must capture policy decisions without duplicating sensitive prompt or memory content. At minimum record decision ID, operation, principal and context identifiers, context epoch, policy version, requested and returned memory IDs, reason codes, route, timestamp, and result. Audit access is itself policy controlled.

Requested/returned IDs are for authorized audit readers, not permission to echo denied identities to callers or generic diagnostics. Denials, counts, filenames, why-not-recalled tools and timing-sensitive diagnostics must not reveal restricted objects. Define the observable timing threat model and retain tests and unresolved limitations; functional content-free errors alone do not establish timing confidentiality or waive this acceptance requirement.

Reclassification, declassification, promotion, retention changes, exports, and policy changes require append-only history with actor, authority, reason, source and destination policy, and effective time. Derived memories retain their full source graph. Deleting or restricting a source must trigger policy-aware handling of derived memories and cached representations.

Restrictions take effect immediately for affected descendants while recomputation is pending. A derivative may become available under a narrower authorized evidence set only after that set fully supports a regenerated result; removing citations cannot authorize the old conclusion. Provider submission, synchronization, and exports honor destination handling rules, including local-only restrictions.

Participant, grant, purpose or policy changes invalidate affected caches and outstanding evidence handles, including work already queued. Long-running and streaming operations must define and test authorization rechecks or cancellation gates before further protected use, provider submission or output delivery. Specify race behavior, epoch ownership and safe resume; request-start verification or a preserved database snapshot alone is insufficient. Already emitted or externally copied text cannot be retracted, so revocation claims must state that boundary rather than promise retroactive erasure.

Durable source-backed memory has an explicit retention policy independent of working-memory TTL/count trimming. Consolidation, aging, pinning, forget, export, and restore must preserve the documented evidence contract. Removing project membership, forgetting memory, deleting an index, and deleting source bytes are distinct operations. Mnemosyne must not delete archive originals implicitly. Audit access, bounded retention, and audit-failure behavior must be specified without requiring an external service.

### Incremental indexing and recovery

Registration is idempotent by source revision, extraction revision, and span identity. Retrying unchanged ingestion, moving files, or changing project membership does not create new embeddings. Content/extraction changes invalidate affected derivatives; model, dimension, or chunk-policy changes create an explicit index generation. Embedding reuse requires an allowed sharing domain and matching text, model, dimensions, and preprocessing contract. Authorization changes are independent of embedding identity.

Imports use bounded transactions and resumable checkpoints with planned/completed/failed/excluded coverage. Interrupted work must not appear complete or publish an inconsistent index, and the existing usable generation remains recoverable. Transcription and document extraction resume independently; media awaiting human preparation does not block already-readable documents.

## Performance Requirements

Authorization must be implemented as indexed query constraints or an equivalent secure prefilter before semantic and lexical ranking. Classification, owner, tenant, context, and compartment relationships must use queryable indexed structures. Storing all policy data only as JSON metadata is insufficient.

The implementation should compile effective context policy once per context epoch and cache safe query plans keyed by the context-policy fingerprint. It should avoid evaluating each candidate in Python after broad retrieval. Vector and full-text recall must generate candidates from the authorized set so policy does not silently damage recall quality.

Release benchmarks must measure unclassified baseline and policy-aware operation at 10,000, 100,000, and 1,000,000 memories; 1, 10, and 100 compartments; single- and multi-participant contexts; cold and warm caches; policy changes; and participant changes. Record ingestion throughput, p50/p95/p99 recall latency, time to first injected memory, policy compilation time, cache hit rate, database and index growth, and authorized recall quality.

Draft performance gate: common contexts with one to three compartments should add no more than 10% p95 recall latency over the same indexed unclassified workload, while returning zero unauthorized candidates. The security gate is absolute: no performance optimization may return, rank, log, or cache unauthorized content. The exact latency target should be confirmed against Mnemosyne's current benchmark suite before an upstream proposal.

### Measurement and refactoring contract

Performance is a standing acceptance concern for correctness and feature changes, not a final optimization phase. Keep the existing query embedding model, dimensions, dataset, dependencies, machine settings, token budget, and request shapes fixed for each comparison. Separate query embedding/provider waits, SQLite/native work, and Python overhead so a network or model change is not credited as an engine refactor.

Start with at most five fixed synthetic request shapes covering representative recall, write/index, evidence expansion, and policy-transition behavior. Repeat baseline and candidate runs enough times to characterize variance and meaningful percentiles; five request shapes are not five latency samples. Compare the immediately preceding accepted checkpoint with the candidate in legacy mode and in a fixed protected context. Record cold/warm cache cases, denied high-ranking distractors, empty authorized results, participant/policy changes, and cancellation/interruption where relevant. Larger capacity benchmarks at the scales above are milestone evidence, not a requirement to run million-row workloads after each edit.

Record request/artifact identity, p50/p95/p99 latency with sample counts, operations/documents per second, injected tokens, embedding calls, peak memory, database/index size, and authorized recall quality. Count documents indexed as external sources, not documents archived in Mnemosyne. Where ranking intentionally changes, use declared relevance expectations and quality metrics; otherwise preserve outputs, ordering, counts, attribution, lifecycle behavior, and persisted contracts. Zero unauthorized disclosure is mandatory regardless of speed.

Profile bounded workloads with cProfile and SQL/query-plan inspection to locate repeated normalization, database reads, serialization, policy compilation, connection/setup work, or unnecessary re-embedding. These are investigation candidates, not established bottlenecks. Native, device, or provider time enclosed by a Python frame is not automatically Python overhead. Make one localized change per hypothesis, run focused correctness tests, and measure the same workload again without the profiler. Accept a performance improvement only if it repeats beyond observed noise without shifting the cost to an unmeasured path or weakening isolation, evidence fidelity, or recall quality. Reject or defer unproven optimizations rather than accumulate alternate paths.

Maintain a small measurement ledger with the frozen workload, baseline/candidate identities, hypothesis, invariant checks, measured delta, resource/quality effects, and disposition. No latency or throughput improvement is claimed without that evidence. The 10% p95 target above remains provisional: planning must select measured budgets before implementation, including acceptable absolute latency and legacy-mode overhead. A repeatable regression must be explained and explicitly accepted or corrected; mandatory security work is not exempt from measurement. No external policy service, remote LLM, or new gateway is required to benchmark or enforce the minimum contract.

## Failure Behavior

- Missing or invalid context: deny protected retrieval and protected writes.
- Unknown participant or stale epoch: deny and request context refresh.
- Policy engine or policy-store failure: fail closed.
- Missing classification with no trusted inherited value: normalize to `unclassified`, preserve its defaulted origin and all other restrictions, and authorize using the complete applicable policy; this is not a public-access grant.
- Unsupported, contradictory or invalid explicit classification: keep pending review and exclude from protected retrieval; never silently downgrade it to `unclassified`.
- Policy change during a request: reject or restart under the new policy version.
- Cache fingerprint mismatch: miss and recompute.
- Derived-memory provenance loss: quarantine the derived memory.
- Import ambiguity: stop for review rather than guess.

## Acceptance Tests

- A public context cannot retrieve internal, confidential, restricted, or private canaries.
- A confidential client context cannot retrieve another client's confidential canaries.
- A client-visible context cannot retrieve firm-internal memories for the same client and matter.
- A healthcare billing context cannot retrieve care information outside its configured minimum-necessary policy.
- An ethical-wall principal cannot retrieve blocked matter memories even with a matching semantic query.
- A newly added participant immediately creates a new context epoch and reduces access as required.
- Changing a chat title or runtime session ID neither grants nor removes authorization.
- Derived memories receive the strictest source classification and complete compartment union.
- Vector, full-text, graph, cache, consolidation, export, and administrative paths pass the same canary suite.
- Invalid document metadata returns the document to pending review and excludes it from retrieval.
- Conversation extracts inherit context classification while remaining pending content review.
- Repeated ingestion and extraction are idempotent and preserve provenance.
- Policy changes invalidate affected caches.
- Audit records explain allow and deny decisions without storing memory content.
- Performance gates pass at each required scale with zero unauthorized candidates.
- The handoff's A1-A18 scenarios pass using synthetic fixtures, with explicit evidence for each covered surface and an implemented/partial/missing status for the remainder.
- Project-specific interpretations remain scoped when their source is shared; project selection cannot expand trusted grants.
- Move, duplicate, offline-volume, same-span correction, and source-revision mismatch scenarios preserve the defined identity and evidence contracts.
- Revocation applies immediately to descendants, issued evidence handles, caches, provider inputs, and exports while recomputation is pending.
- SDK, CLI, MCP, and Hermes paths enforce the same policy; outputs, evidence expansion, and model/reranker inputs are inspected for denied canaries.
- Durable evidence survives permitted maintenance; unchanged/resumed imports preserve counts and explicit coverage without discarding the prior usable index.
- Existing scope/bank/media/resolver regressions remain part of acceptance, alongside recall-quality and latency measurements with restricted top-ranked distractors.
