## Fact, conflict, and privacy review

The browser's Listen control is injected by the post layout only outside production. It uses a JavaScript extractor on the current DOM and a 900-character chunk target. The Python CLI fetches rendered HTML through `requests`, extracts from `.post-content.e-content`, and defaults to 1,200-character chunks. Both preserve readable link labels and inline code words while removing raw URL links, code blocks, tables, and page furniture. `blog_diagram.html` places its optional caption in a paragraph outside the figure, so that paragraph can still be spoken; the Part 7 prose says so. A dry run of the local Part 7 route initially exposed awkward spoken selector and URL examples; the article was edited to remove them.

The browser relay listens only on loopback and checks allowed origins. It forwards each text chunk to a configured speech endpoint and returns the complete audio response. Browser playback prepares the next chunk while the current one plays. Safari uses a native audio element and primes output in the button gesture; other supported browsers use Web Audio. Do not call this byte-level streaming, or claim that a source review proves the user's particular voice/bridge is available.

`utils/bin/article-tts --browser-server` is the actual long-running local browser relay. It requires `--bridge` or `TTS_BRIDGE_URL`; the locally configured voice may come from `TTS_BRIDGE_VOICE`. The `jekyll-site` wrapper starts Jekyll but contains no article-TTS startup or shutdown path. The public article now shows the helper command and says to leave it running separately. On September 28, a local `GET /health` with allowed origin `http://localhost:4000` returned HTTP 200 and `{"status":"ok"}` on port 11441; that proves only the relay listener was alive, not upstream synthesis.

The Publisher reports that the configured upstream is the LLM-Ops-Kit-managed TTS Bridge and that patched MLX-Audio supplies the voice-cloning synthesis. The earlier published Local First AI article and LLM-Ops-Kit cloning guide support the division of responsibility: site loopback relay, managed bridge with a stable speech contract and alias mapping, then engine-owned registered references and synthesis. Part 7 gives that path one paragraph and links the earlier article rather than repeating its operational treatment. This is an attributed current setup, not a live synthesis test from the website checkout.

The article must not publish a private TTS endpoint, voice alias, model path, voice sample, recording, transcript, or model configuration. The public diagram names only the loopback relay and configured bridge; the paragraph supplies the underlying engine distinction. The browser proofreading path writes no audio file; the CLI without `--dry-run` has a different retained-output path, and `article-audio` has a separate publication workflow. Avoid saying that no tool ever writes audio.

The Publisher's August post supplies the personal narrative and candor. Keep the installment in first person, with the point returning to proofreading after explaining the technical path. Do not invent an example sentence or listening result that the Publisher has not supplied. Part 7 should not imply editorial approval of any generated narration.
