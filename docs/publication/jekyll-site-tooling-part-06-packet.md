## Fact and conflict review

The viewer is a separate full-browser page in a new tab. Earlier outline language calling it an “overlay” is inaccurate and must not appear in the article. The shared include links both image and caption to that viewer. Its JavaScript accepts only same-origin URLs with an `.svg` pathname; it does not fetch or sanitize an arbitrary SVG. The article can state only the observed browser interaction and source restriction.

The `source_code_highlight` filter resolves the source path and the allowed `assets/code` root to real paths before it reads, rejecting resolved paths outside that root. The disclosure's download link points to the supplied path. Thus the rendered highlighted code and downloadable artifact are sourced from one file in the normal include path. This does not prove the code runs, is safe to execute, or has an external reuse license.

The article should treat awkward ASCII diagrams, giant SVGs, and forced downloads as editorial problems to solve, without inventing an undocumented migration sequence. The viewer's page move in the changelog is a route-preserving organization change, not the origin story for the design. The second Part 6 figure now uses an actual `.mmd` source and `mmdc`; its percentage-width SVG is normalized to dimensions from `viewBox`. Do not imply every existing SVG was generated or normalized by one script.

## Embedded-source automation proposal

The explicit single-source renderer is now implemented and locally exercised for both Part 6 figures. Automatic integration remains a candidate, not implemented site behavior. A reviewed manifest could map stable diagram IDs to `.dot` or `.mmd` files, renderer settings, SVG/PNG output paths, and the existing article include. A pre-build command would render changed diagrams before Jekyll reads the site; CI would check that committed outputs match their inputs. Do not make pre-commit silently rewrite assets, because a commit could then capture an unreviewed visual change. Pre-commit can run a read-only stale-output check.

An embedded-Markdown second phase would use opt-in `dot` or `mermaid` fenced blocks with explicit stable IDs, alt text, and captions. A preprocessor or Jekyll extension would extract only those blocks, render the files, and substitute the same `blog_diagram.html` presentation in derived content without editing the author's Markdown. Mermaid CLI already supports transforming Mermaid blocks in Markdown into linked SVGs, but it does not provide this site's DOT support, captions, viewer markup, or archive policy; that remains custom integration. Avoid timestamps: hash the block content together with renderer/version/theme settings and record it beside the output. A prose-only edit then leaves the diagram untouched, and a fresh checkout does not create false staleness. The build should fail clearly if the requested renderer is missing or a block has no stable ID or alt text. A small isolated Jekyll fixture should prove both source preservation and rendered output before touching the main site wrapper or CI.
